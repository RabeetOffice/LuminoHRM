# Lumino HRM Phase 5 (Payroll) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** HR generates a month's payroll from the attendance and leave already in the system, reviews and adjusts it, Admin approves it, payslips are emailed as PDFs, the bank gets one transfer sheet, and an approved month is frozen against every later change.

**Architecture:** Four layers kept apart. (1) **Records**: salary profiles (+ components) with history, loans (+ repayments, skips), opening balances, payroll runs, payroll items (figures + frozen JSON breakdown + bank snapshot), adjustments; all money is integer paisa. (2) **Rules**: a pure `PayCalculator::calculate(PayInput): PayResult` holds every money rule; `PayInputLoader` gathers inputs for many people in a fixed number of queries (MonthGrid cells, unpaid leave by date, profiles, loans, settings); `PayrollRoster` decides who is in a run; `PayrollChecks` decides what blocks approval. (3) **Actions**: generate / recalculate / line inputs / approve / mark paid / delete, each in one transaction locking the run row first, audited, mails and payslip jobs after commit. (4) **Lock**: `PayrollLock::isLocked()` is true for approved months and every attendance, leave, holiday, employment-date and salary write refuses or skips locked dates.

**Tech Stack:** As Phases 0–4 (Laravel 13, PHP 8.4, Inertia + React + TypeScript, Tailwind 4, shadcn/ui, Wayfinder, spatie permission + activitylog, maatwebsite/excel, Pest, Vitest). New: `barryvdh/laravel-dompdf` (pure PHP, works with `exec` disabled; named in the main design's stack table), installed by Task 9 only.

**Spec:** `docs/superpowers/specs/2026-11-25-phase-5-payroll-design.md` (wins where it differs from the main design) and `docs/superpowers/specs/2026-11-23-lumino-hrm-design.md` sections 8 (roles: Payroll Admin "Run, approve, lock", HR "Run, edit draft", Manager none, Employee own payslips; salary rule line 193), 9.1 (Payroll This Month tile, employee's latest payslip), 9.2 (Salary tab, Admin/HR only), 9.3 (late rule per month rounded down; missing clock-out blocks approval; half days), 9.5 Payroll, 9.8 (final settlement is Phase 6), 9.9 (settings), 9.10 (audit), 11 (data model), 13 (risks), 14 (defaults: tax on gross taxable, overtime off, encashment off; item 13 answered: calendar month, paid in the first days of the next month).

**Builds on:** Phase 4 as built (branch `phase-4`; plan `docs/superpowers/plans/2026-11-25-phase-4-leave.md`; ledger `.superpowers/sdd/2026-11-25-phase-4-leave/progress.md`; agent rules `.superpowers/sdd/2026-11-25-phase-4-leave/agent-rules.md`). ## Open decisions (defaults chosen; owner may change)

The design (section 7) lists them; each is marked "(default, owner may change)" where a task uses it.

1. **Rounding:** every computed amount half up to the whole rupee (`Money::div`); entered amounts whole rupees.
2. **Day-pay basis** default `calendar_days` (existing setting); `thirty` and `working_days` (whole month minus the employee's weekly offs and holidays; 0 → calendar days) supported; proration always by calendar days.
3. **Source of deductions:** unpaid leave from `leave_days` on every day of the pay window (also before `attendance.start_date` and on manual days); absences, half days and lates from attendance only on days `MonthGrid` counts; per date at most one day (2 halves); unpaid leave on a `holiday`/`weekend` day not deducted (warning).
4. **Fixed deductions and fixed tax** prorated by calendar days; not reduced by absences.
5. **Tax** mode and rate from the profile in force on the last day of the pay window; percentage base after the attendance deduction's taxable (or basic) share.
6. **Late-rule days** charged at the last profile of the month; `late_rule_count` 0 = off.
7. **Pay short of deductions:** loan installments reduced (oldest loan first); still negative → blocks approval.
8. **Overtime** settings in the Attendance group: `overtime_rate_mode` `multiple`, `overtime_multiplier_percent` 150, `overtime_fixed_rate` 0, `overtime_hours_per_day` 8; `overtime_enabled` stays false.
9. **Generation window:** any month ≤ the current month and > the latest locked month; approval only after the month ends (`month < substr(attendanceToday(), 0, 7)`) and in month order.
10. **No re-opening** an approved run; corrections are next-month one-off items.
11. **Own line:** an approver whose own line is in the run may approve only as the sole active Admin (audited `own_payslip: true`).
12. **Payslip email** attaches the PDF.
13. **Bank sheet:** one generic `.xlsx` (sheet 2: lines without a bank account).
14. **Tax year** July–June (`payroll.tax_year_start_month` = 7), named by start year, shown "2026-27".
15. **Leavers** in their final month ("Settled separately") and leavers without a last working day ("Left, no last working day") are listed, never paid by the run.
16. **Loans** disbursed outside the system; payroll only recovers.
17. **HR sees every salary** (incl. Admin's) but edits only non-privileged people other than themself.
18. **Dashboard tile** = run of the previous calendar month.
19. **PDF:** `barryvdh/laravel-dompdf`, A4, DejaVu Sans.

## Review Focus

1. **Approval races** — a leave approval, attendance correction, profile save, loan repayment or line edit committed while Admin approves → approval either sees it (recalculated, "figures changed") or the write waits on the run row's lock and is then refused as locked; nothing is half-applied. Tests in Tasks 1, 6, 7.
2. **Arithmetic edges** — every worked example of design 5.3 (joiner 16 Nov, joiner 10 Dec, raise on 16 Nov, Feb under `thirty`, Nov under `working_days`, overtime, half-rupee rounding), the per-date cap, half-day leave combinations, pay short of deductions. Tests in Task 2 (pure) and Task 3 (loaded from real rows).
3. **Source conflicts** — unpaid leave before `attendance.start_date`, on a manual worked day, on a weekend after a shift change; exempt staff; leaver in / after the final month; leaver without a last day; joiner after the month. Tests in Task 3.
4. **Privacy** — Manager and Employee on every payroll route and id (runs, items, profiles, loans, payslip PDFs, exports, tax report), dashboard and profile props, My Payslips of someone else → 403 / absent; HR editing own or an Admin's salary, line or loan → 403. Tests in Tasks 4, 5, 8, 9, 10, 11.
5. **Immutability** — after approval: editing a profile, a setting, a loan or a bank account changes no stored line, PDF bytes re-rendered from storage equal the first render's text, attendance / leave / holiday / employment-date writes in the month are refused, the rebuilder skips locked days. Tests in Tasks 6, 7, 9.

## Shared interfaces

- **`App\Support\Payroll\Money`** (Task 1): `div(int $n, int $d): int`, `rupees(int $rupees): int` (× 100), `format(int $paisa): string`, `bp(string $percent): int` (`"5"`/`"5.25"` → 500/525; at most 2 decimals; 0–10000).
- **`App\Support\PayrollLock`** (Task 1, real): `isLocked(string $month): bool`, `firstLocked(iterable $dates): ?string` (unchanged signature), `lockedMonths(array $months): list<string>` (one query), `latestLocked(): ?string`, `rangeTouchesLocked(string $from, string $to): ?string` (first locked `Y-m` between two `Y-m-d` dates inclusive, either order), `message(string $month): string` ("Payroll for November 2026 is approved, so this can no longer change.").
- **Payroll lock in writes — lock order** (Task 6): the global order is **employee rows → `payroll_runs` (shared, the `PayrollLock` read) → attendance / holiday / leave rows**; the approval (Task 7) takes `payroll_runs` (for update) → loans and must take no row lock on employees, attendances, holidays, attendance corrections or leave rows (plain reads only), so no cycle exists. Never `latestLocked()` inside a write transaction. Where each Task 6 write reads the lock:
  - `ApplyManualCorrection` (Daily save, request apply): first statement of its transaction, before the attendance row lock (and a plain pre-check before it for the message).
  - `CorrectionRequests::submit`: after the employee row lock (its first statement, unchanged), through `CorrectionEligibility`; `decideAsHr` (approve): after the request row lock, before the attendance row lock.
  - Daily reset: first statement, before the attendance row lock.
  - `AttendanceRebuilder::process`: first statement of each batch transaction (`lockedMonths` over the batch's months), before the attendance row locks; `closeDay` / `daysWithMissingRows`: plain reads outside a transaction.
  - `RebuildMarks::*`: one `lockedMonths` per call, before its UPDATE; when called inside an employee save it comes after the employee row lock. Exception (Task 6 fix round): the "from today" paths (`forShift`, `forEmployeesWithoutShift`, `forEmployee`) read no lock at all — their rows are dated from the current attendance day on, and approval refuses a month that has not ended, so they can never be in a locked month; this removes the shift-path cycle (shift row → `payroll_runs` vs run write → employees of that shift).
  - `PunchIngestor::markDays` / relink: one `lockedMonths` per call; dates in a locked month get no row and no flag (the punch is still stored). `AttendanceRebuilder::finaliseManual` and the safety-net updates of `closeDay` re-read `lockedMonths` inside their transaction and skip a month approved meanwhile.
  - All `PayrollLock` readers select `payroll_runs` rows by month only (equality, list or range on the unique `month` index) with `LOCK IN SHARE MODE` and filter the status in PHP, so a draft run row in the range is share-locked too and a concurrent approval of it waits for the reader.
  - `HolidayController` store / update / destroy: first statement, before the holiday row lock. Known exception: the holiday refund (Phase 4 `HolidayLeaveRefund`) locks leave rows and then employee rows later in the same transaction, i.e. after `payroll_runs`. Two cycles remain, both through a holiday save that refunds leave: (1) holiday-with-refund (holds `payroll_runs` shared, wants employee X) vs generate / recalculate (holds the run's employees shared, wants the run row for update); (2) holiday-with-refund vs a per-employee writer (holds employee X, wants `payroll_runs` shared) while an approval waits for the run row for update (InnoDB queues the writer's shared request behind the waiting exclusive one). All run-level writes, the holiday save and the per-employee writers run in `DB::transaction(fn, 3)`; InnoDB detects either cycle, rolls one transaction back and it is retried — a deadlock error at worst after three tries, never a hang.
  - `UpdateEmployee` (joining date) / `ChangeEmployeeStatus` (last working day): after the employee row lock, before any attendance / leave write.
- **Payroll lock order — run-level writes** (Task 1 fix round, ruling; Task 7 implements; supersedes the sentence above that the approval takes no row lock on employees): the order is **employee rows → `payroll_runs` row** everywhere. Per-employee writers (leave, attendance, salary profiles, loans) lock the employee row first and then call `PayrollLock` (shared). Run-level writes that insert, change or delete payroll lines (generate, recalculate, approve) FIRST take shared locks on all the run's employees in id order (`Employee::query()->whereIn('id', $ids)->orderBy('id')->sharedLock()->get(['id'])`), THEN `lockForUpdate()` the run row; the run row lock is the first statement after the employee locks (no plain read of the run before it: under REPEATABLE READ that fixes the snapshot). Never call `PayrollLock` (shared) and then `lockForUpdate()` the same run row in one transaction (upgrade deadlock). Avoid `latestLocked()` inside write transactions. `PayrollLock` reads are plain top-level `SELECT … LOCK IN SHARE MODE` (never `exists()`). Safety net in the models: `PayrollRun` status only moves draft → approved → paid and an approved/paid run is never deleted; an existing `PayrollItem` of an approved/paid run cannot be changed (except `payslip_path`, `payslip_generated_at`, `payslip_emailed_at`) or deleted, its run status read from the database, so the approval copies the bank snapshot onto the lines before setting the run to approved.
- **`App\Support\Payroll\PayrollAccess`** (Task 1): `mayEditSalary(User $by, Employee $e): bool`, `mayApprove(User $by, PayrollRun $run): bool`, `approvesOwn(User $by, PayrollRun $run): bool`, `soleActiveAdmin(User $u): bool`.

### Task 2: Pay calculator (pure)

**Files:** Create `app/Support/Payroll/PayCalculator.php`.
**Tests:** `tests/Unit/Payroll/PayCalculatorTest.php` (pure; builds `PayInput` by hand with a local `input(array $overrides): PayInput` builder; no database).

**Interfaces — Consumes:** Task 1 DTOs and `Money`.

**Interfaces — Produces:** `PayCalculator::calculate(PayInput $in): PayResult` — static, pure, no I/O, no settings or clock reads. Rules in this order (design 5.3; pin each with the examples below):
1. Segments as given (the loader splits the pay window at profile effective dates and drops days with no profile; `daysPaid` = sum of segment days). No segments → result with all zeros, `blocking = ['no_profile']`.
2. Per component and segment: earned = `Money::div(amount × days, daysInMonth)`; earnings lines per component name (same name across segments summed into one line); `basic`, `allowances`, `gross`, taxable gross accordingly. Fixed deductions per segment the same way → `fixedDeductions`, one line per name.
3. Deducted halves per date: for each date in `attendanceHalves ∪ unpaidLeaveHalves`: `unpaid = in_array(date, offDates) ? 0 : unpaidLeaveHalves[date] ?? 0` (an ignored unpaid date adds warning `unpaid_leave_on_off_day`); `halves = min(2, (attendanceHalves[date] ?? 0) + unpaid)`; a date in `manualWorkedDates` with unpaid > 0 adds warning `unpaid_leave_on_worked_day`. Exempt (`$in->exempt`) → attendance halves treated as 0 (unpaid still counts). Late halves = `lateRuleCount > 0 && !exempt ? intdiv(lateDays, lateRuleCount) * 2 : 0`, assigned to the last segment. Dates are assigned to the segment containing them; a date in no segment is ignored.
4. Attendance deduction = Σ segments `Money::div(segment gross × halves, 2 × basisDays)`; taxable share and basic share likewise with `taxableGross()` / `basic`; each capped at the earned gross / earned taxable gross / earned basic. Label "Attendance (N days)" with N = halves ÷ 2 formatted like "4.5".
5. Overtime (only when `overtime->enabled` and minutes > 0 and not exempt): mode `multiple` → `Money::div(lastSegmentGross × minutes × multiplierPercent, basisDays × hoursPerDay × 60 × 100)`; `fixed` → `Money::div(fixedRatePaisa × minutes, 60)`. Taxable. Label "Overtime (N h M min)".
6. Adjustments: additions add to gross (taxable per flag); deductions → `otherDeductions`.
7. Tax: override present → that amount (`overridden` true). Else by the last segment's mode: `none` 0; `fixed` → Σ segments `Money::div(taxValue × days, daysInMonth)`; `percentage` → base = (`gross_taxable`: earned taxable gross − taxable share + overtime + taxable additions; `basic`: earned basic − basic share), `taxablePay` = that base (for `none`/`fixed`, `taxablePay` = the gross-taxable base anyway, for the tax report), tax = `Money::div(base × bp, 10000)`.
8. Net before loans = gross − attendance − fixed − other − tax. Negative → `blocking[] = 'negative_net'`, no loan deducted.
9. Loans oldest first: skipped → 0 (line kept with amount 0 and label "… (skipped this month)"); else `due = min(installment, remaining)`, deducted `min(due, net so far)`; a reduction adds warning `installment_reduced`. `loanDeductions` map.
10. `breakdown` exactly as the Shared interfaces JSON (version 1), with `attendance` from `attendanceTotals` plus `unpaid_leave` (Σ unpaid halves ÷ 2 counted), `paid_leave` (= max(0, `on_leave` − unpaid_leave)), `late_days_deducted`, `deducted_halves`, `counted_from`.
